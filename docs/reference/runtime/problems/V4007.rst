=====
V4007
=====

.. problem-summary:: V4007

Online change refused the candidate because its state layout is incompatible
with the running application and the runtime cannot carry the state across the
difference. The state layout is the part of the application that holds values
between scans: the global variables, the variables of the program, the arrays
they use, and the fields of function blocks (the container's
``layout_hash`` and the extent it covers), together with the header flags. A
candidate that changes any of them without a migration plan is rejected so the
running application keeps executing with its state byte-for-byte intact.

Statements are not part of the layout, and neither are the calls a statement
makes: adding the first call of a function, or removing the last one, is an
ordinary online change, as is any change to the parameters and local variables
of a function. Only a change to a declaration of persistent state — a variable
added, removed or given another type, an array bound, a function block field —
changes the layout.

Example
-------

A session stages a candidate compiled from a program that adds a variable,
but the candidate was compiled without the stable variable IDs a migration
needs. The command is accepted on the wire and refused by the host:

.. code-block::

   {"command":"acceptEdits","program":[...]}
   {"response":"error","vCode":"V4007","message":"candidate layout is incompatible with the active application"}

The candidate was not staged; a later ``getStatus`` reports no candidate.

To fix this error, compile the candidate from a source edit that keeps the
state layout unchanged (a code-body edit, including calls to functions, or a
rename when stable variable IDs are assigned), or assign stable variable IDs so
a declaration-level edit can migrate per variable. Until a schema edit can be migrated, apply it as a
cold start: stop the runtime and load the new container. See
:doc:`V4010` for the migration case and :doc:`V4016` for payloads that are
not containers at all.
