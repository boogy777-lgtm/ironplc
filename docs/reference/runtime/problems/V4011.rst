=====
V4011
=====

.. problem-summary:: V4011

``untestEdits`` or ``cancelEdits`` was requested while a schema-changing
candidate — a migration candidate whose layout hash differs from the running
application's, or a candidate accepted in ``replace`` mode (a download) — is
under test. Writes made under the candidate's layout have no
reverse mapping for the variables the candidate added or removed, and the old
buffers are not kept, so reverting the code would strand state that belongs to a
layout that no longer executes. Cancelling a candidate under test reverts it
first, so it is refused for the same reason. The runtime
refuses the command and leaves the candidate active with the state untouched.

Example
-------

A session accepts a candidate that adds a variable, tests it, and then asks
to revert:

.. code-block::

   {"command":"acceptEdits","program":[...]}
   {"response":"ack"}
   {"command":"testEdits"}
   {"response":"ack"}
   {"command":"untestEdits"}
   {"response":"error","vCode":"V4011","message":"untest and cancel are not supported after a schema-changing test; assemble instead"}

To proceed, send ``assembleEdits``: it commits the candidate, the migration is
applied, the new schema becomes the running application, and the application
generation advances. It is the only exit of a migration candidate under test.
Before ``testEdits`` the original artifact is still active, and
``cancelEdits`` discards the candidate. The same holds for a download: a candidate accepted in ``replace`` mode
(``testingReplace`` in the edit view) is rebuilt from its initial values at the
test, the old state is not kept, and ``assembleEdits`` is its only exit after the
test (see :ref:`ironplcvm-replace`).
A logic-only edit keeps its untest
path and can be cancelled from the test as well, as described in the online
change protocol.
