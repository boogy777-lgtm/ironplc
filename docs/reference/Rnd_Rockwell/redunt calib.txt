Да. Я бы здесь заложил фундамент так, чтобы потом не пришлось переписывать прошивку I/O при развитии redundancy.

Ключевой принцип:

PLC redundancy layer решает, кто имеет право попытаться стать Active. I/O firmware решает, имеет ли конкретный PLC право физически воздействовать на выходы.

То есть I/O — последний fencing layer, но не election/quorum node.

Это продолжает уже принятую модель: ACTIVE имеет Exclusive Owner, не-ACTIVE наблюдает через Input Only; причём Input Only принципиально лучше Listen Only, потому что не зависит от существования owner. Такой подход соответствует EtherNet/IP: output-модуль допускает только одного owner, и именно firmware модуля обязана это обеспечить.

1. Граница ответственности

Я бы жёстко разделил:

Функция	PLC HA runtime	I/O firmware
DUTY / RESERVE	✓	не знает
PING/PONG между PLC	✓	нет
Link calibration пары	✓	предоставляет метрики
SYNC_READY	✓	не знает
Решение о takeover	✓	нет
Epoch generation	✓	проверяет
Exclusive ownership	запрашивает	enforces
All-I/O barrier	координирует	подтверждает локальный claim
Output arm	командует	enforces
Owner timeout	наблюдает	детектирует локально
Safe state	задаёт policy	исполняет аппаратно
Фактический output	формирует	последнее решение

Главное следствие:

RESERVE никогда не говорит I/O:

"Primary умер, поверь мне".

Он говорит:

"I request ownership
 for Pair X
 Controller B
 candidate Epoch 42"

А модуль сам решает:

current owner exists?    → reject
epoch invalid?           → reject
config incompatible?     → reject
faulted?                 → reject

otherwise                → claim accepted

Сейчас сигнал I определяется косвенно: резерв видит изменения input data, которые якобы свидетельствуют, что peer владеет I/O.

5. Почему CLAIMED_DISARMED нам нужен

Пусть Secondary должен получить пять output-модулей:

DO1 ✓
DO2 ✓
DO3 ✓
DO4 ✗
DO5 ?

Если DO1–DO3 уже начали физически применять output нового PLC, мы получили частичный takeover.

А наш инвариант говорит:

partial ownership != ACTIVE

Поэтому acquisition означает только:

Exclusive Owner acquired
        ↓
CLAIMED_DISARMED

Физические выходы всё ещё:

SAFE / HOLD / configured takeover state

Контроллер получает ownership всех required modules:

DO1 CLAIMED_DISARMED ✓
DO2 CLAIMED_DISARMED ✓
DO3 CLAIMED_DISARMED ✓
DO4 CLAIMED_DISARMED ✓
DO5 CLAIMED_DISARMED ✓

Только тогда:

OWNERSHIP_BARRIER = PASSED

и начинается отдельная фаза:

ARM

Это превращает нынешний all-or-nothing barrier из логического правила в реальное свойство firmware I/O.

6. Это фактически двухфазный takeover

Получаем:

   ↓

   ↓
I/O CLAIMED_DISARMED
   ↓
verify ALL modules


PHASE 2 — COMMIT

   ↓

Если acquisition одного модуля провалился:

но они и так никогда не воздействовали на процесс.

Это очень сильный фундамент.

13. Никакого Listen Only в HA

Это уже правильно заложено в текущей спецификации: Listen Only зависит от существующего owner; Input Only — самостоятельный.

То есть:

14. Local owner watchdog

У output firmware должен быть собственный аппаратно/RT ограниченный watchdog O→T connection.

Пример состояния:

owner_connection_timeout
owner_age

Если:

owner_age >= effective_connection_timeout

модуль самостоятельно:

OwnerArmed = FALSE
apply FaultAction
release owner when CIP connection declared timed-out

Secondary здесь вообще не участвует.

Очень важный принцип:

I/O safety никогда не зависит от того, успел ли резервный PLC принять решение.

15. Fault output policy

Для каждого output channel уже в common core надо заложить policy abstraction.

Rockwell, например, позволяет output-модулю при потере owner перейти к заданному fault value, удерживать значение и для analog output применять ramp.

Нам нужны как минимум режимы:

Policy	Поведение
SAFE_VALUE	немедленно заданное fault value
HOLD_LAST	удержание последнего
RAMP_TO_SAFE	AO плавно к safe value
CHANNEL_POLICY	специализированная логика модуля

Для HA default я бы оставил SAFE_VALUE.

HOLD_LAST — сознательная engineering policy, не скрытое поведение redundancy.

17. Тогда ownership-barrier тоже становится формулой реальности

Для последовательного v1:

$$ T_{claim} = \sum_{i=1}^{N} T_{claim,i} $$

Но Studio сможет иметь:

$$ \hat T_{claim} = \sum EMA_{claim,i} $$

и qualification bound:

$$ T_{claim,max} = \sum MaxQualified_{claim,i} $$

Если позднее разрешим parallel Forward_Open:

$$ T_{claim} \approx \max_i(T_{claim,i}) $$

Прошивку I/O при этом менять практически не потребуется.

Ethernet ip поддерживает постоянное соединение или нужно его поднимать во время перехода ? Этот edge case должен архитектурно закрыт

Да. Этот edge case критичный, и его надо закрыть двумя режимами I/O ownership, потому что стандартный EtherNet/IP и «настоящий preconnected HA» ведут себя по-разному.

В обычном EtherNet/IP Class 1 I/O-соединение после Forward_Open является постоянным циклическим соединением: контроллер и адаптер обмениваются implicit I/O по RPI, пока connection жив. Но для стандартного output-модуля разрешён только один Exclusive Owner; попытка второго контроллера открыть ещё один owner connection должна быть отвергнута firmware модуля.

Поэтому стандартный сценарий выглядит так:

PRIMARY A                           I/O
   │
   │  Forward_Open Exclusive Owner
   ├──────────────────────────────►│
   │                               │
   │   cyclic O→T / T→O @ RPI      │
   │◄══════════════════════════════►│
   │                               │
SECONDARY B                        │
   │                               │
   │  Forward_Open Input Only      │
   ├──────────────────────────────►│
   │◄════ cyclic T→O observer ═════│

Secondary может всё время быть подключён к I/O, но как Input Only. Такие соединения независимы, и несколько originator'ов могут держать их одновременно.

А вот второе Exclusive Owner стандартный output-модуль заранее держать не может.

Что происходит при отказе Primary

Если A просто умер, его Exclusive Owner connection не исчезает в ту же наносекунду:

A DEAD

I/O:
Owner = A
connection watchdog still counting...

Модуль должен сначала установить, что connection A истёк.

До этого:

B → Forward_Open Exclusive Owner
                 ↓
             REJECT
       ownership conflict

Rockwell прямо документирует такой rejection как ownership conflict: output module уже принадлежит другому controller.

Когда старое соединение действительно timed out:

Owner A connection timeout
        ↓
outputs → configured fault/safe policy
        ↓
Owner = NONE

тогда B может успешно выполнить:

Forward_Open Exclusive Owner
        ↓
CLAIMED_DISARMED
        ↓
verify
        ↓
ARM

Поэтому старая формула из нашей спецификации была по сути правильной:

$$ T_{takeover} = T_{detect} + T_{old-owner-release} + T_{ForwardOpen} + T_{validation} + T_{scan} $$

В загруженной спецификации этот old-connection timeout + Forward_Open уже был включён в takeover time.

И вот T_old-owner-release нельзя забывать. В некоторых конфигурациях именно он может стать крупнейшей частью failover.

Но для наших собственных I/O мы можем сделать лучше

Rockwell уже показывает второй путь: существуют output-модули с режимом Redundant Owner, где два controllers могут иметь заранее установленные redundant connections, а в выходных данных существуют OwnerClaim и OwnerReady. Модуль сам выбирает, чьи outputs применять.

Это принципиально другая архитектура:

PLC A                         I/O                         PLC B
  │                            │                            │
  ├════ Owner A connection ═══►│◄═══ Owner B connection ══┤
  │                            │                            │
  │ OwnerReady=1               │               OwnerReady=1│
  │ OwnerClaim=1               │               OwnerClaim=0│
  │                            │                            │
  │                         ACTIVE=A                       │

То есть оба connections уже подняты до аварии.

При отказе A:

Owner A stops
        │
        ▼
B already has connection
        │
OwnerClaim B
        ▼
I/O arbitration
        ▼
ACTIVE=B

Нет критического:

new TCP connection
Forward_Open
wait for configuration
create Class1 connection

на пути takeover.

Это именно тот architectural hook, который нам надо заложить сейчас.

Я бы поэтому ввёл capability I/O-модуля

Не просто:

OwnershipCapability:
    SINGLE_EXCLUSIVE
    REDUNDANT_PAIR

как я предложил выше, а сделал это фундаментальным contract.

Mode 1 — SINGLE_EXCLUSIVE

Совместимость с обычным EtherNet/IP I/O:

PRIMARY:
    Exclusive Owner = persistent

SECONDARY:
    Input Only = persistent

При takeover:

PEER_FAILED
    ↓
wait/verify old owner released
    ↓
Forward_Open Exclusive Owner
    ↓
CLAIMED_DISARMED
    ↓
global barrier
    ↓
ARM

Формула:

$$ T_{claim}^{single} = T_{owner-release} + T_{ForwardOpen} + T_{verify} $$

Это позволяет IronPLC работать с чужими стандартными EtherNet/IP output-модулями.

Mode 2 — REDUNDANT_PAIR

Для наших RegulBUS/IronPLC I/O.

Оба PLC устанавливают connections при qualification пары, а не во время аварии:

              I/O

PLC A ───── OwnerChannel A ─────┐
                                ├── Redundant Owner Guard
PLC B ───── OwnerChannel B ─────┘

У каждого:

PairId
ControllerId
Epoch
OwnerReady
OwnerClaim
OutputSeq
CommitId
OutputData

Но физически применяется только один:

AppliedOwner = A XOR B

И firmware обеспечивает:

never:
    AppliedOwner=A && AppliedOwner=B

Тогда takeover уже:

$$ T_{claim}^{redundant} \neq T_{ForwardOpen} $$

Потому что connection уже существует.

Вместо этого:

$$ T_{claim}^{redundant} = T_{owner-failure-confirm} + T_{arbitration} + T_{ARM} $$

И это потенциально намного быстрее и, главное, намного детерминированнее.

Но я бы не позволял самому I/O решать, что Primary умер

Здесь тонкий момент.

Rockwell Redundant Owner допускает arbitration непосредственно в модуле. Нам для нашей модели лучше сохранить separation:

I/O knows:

connection A alive/dead
connection B alive/dead
epoch A/B
OwnerReady A/B
OwnerClaim A/B

Но право на переход должно требовать корректный claim Secondary.

То есть нельзя:

connection A timeout
        ↓
автоматически применить B outputs

Только:

A unavailable
        +
B connection valid
        +
B OwnerReady
        +
valid newer epoch/claim
        ↓
B may become armed

Так I/O остаётся fencing authority, а не полноценным HA election node.

Я бы ещё разделил CONNECTED и ARMED

Это теперь особенно важно.

Для нашего модуля:

ConnectionState:

DISCONNECTED
CONNECTED_OBSERVER
CONNECTED_OWNER_STANDBY
CONNECTED_OWNER_ACTIVE

Отдельно:

OutputState:

DISARMED
ARMED
FAILSAFE

Получается нормальная redundancy pair:

PLC A:
connection = OWNER
ready      = true
claim      = true

PLC B:
connection = REDUNDANT_OWNER
ready      = true
claim      = false

I/O:
AppliedOwner = A

При controlled switchover:

B:
epoch 42
claim 0 → 1

и только после проверки:

AppliedOwner = B

Connections при этом вообще не меняются.

Это закрывает ещё один опасный edge case

Представим сеть загружена именно во время аварии.

В standard mode:

Primary dies
    ↓
Secondary needs Forward_Open
    ↓
explicit-message path congested
    ↓
connection establishment delayed

То есть:

$$ T_{ForwardOpen} $$

имеет существенный network/scheduler jitter.

В preconnected mode:

Class 1 B already running

Мы всё время измеряем:

packet loss
sequence
jitter

до аварии.

Поэтому наша calibration philosophy начинает работать даже лучше:

Owner A connection quality
Owner B connection quality

известны постоянно.

Перед тем как дать:

TakeoverReady = TRUE

мы можем потребовать:

all required I/O:

OwnerAConnection == VALID
OwnerBConnection == VALID
SecondaryPathCalibrated/qualified

Это очень сильный invariant.

Я бы изменил readiness именно так

Сейчас:

SYNC_READY

ещё недостаточно.

Добавляем:

IO_READY

где:

IO_READY =
    all_required_inputs_observable
 && all_required_outputs_standby_connected
 && all_configs_match
 && all_epochs_valid

Для generic I/O SINGLE_EXCLUSIVE:

standby_connected =
    InputOnly connection valid

Для нашего REDUNDANT_PAIR:

standby_connected =
    RedundantOwner-B connection valid
 && OwnerReady-B

И:

$$ TakeoverReady = SYNC\_READY \land IO\_READY \land RedundancyLinkValid $$

Это существенно сильнее текущей модели.

Для стороннего generic EtherNet/IP:

Для нашего output module v1 я теперь серьёзно рассматривал бы сразу:

REDUNDANT_PRECONNECTED_OWNER

а не откладывал его обязательно на v2.

Потому что это не косметическая optimization. Оно меняет фундаментальный член:

$$ T_{old-owner-release}+T_{ForwardOpen} $$

в takeover path.

Но поддержку SINGLE_EXCLUSIVE всё равно оставляем обязательно

Потому что IronPLC должен уметь резервироваться с обычным EtherNet/IP I/O.

Тогда runtime заранее рассчитывает разные recovery models:

Module DO-1
mode = REDUNDANT_PRECONNECTED

Ttakeover contribution:
0.72 ms measured


Module DO-2
mode = SINGLE_EXCLUSIVE

Ttakeover contribution:
owner timeout  + Forward_Open + verify
= 8.4 ms measured

И Studio честно покажет:

DO-1   preconnected     0.72 ms
DO-2   reconnect        8.40 ms  ← limiting device
DO-3   preconnected     0.81 ms

Worst ownership recovery = ...

Это идеально совпадает с нашей новой парадигмой «не обещаем время — измеряем реальный topology и вычисляем время перехода».

Поэтому архитектурное решение я бы зафиксировал так

EtherNet/IP connection к I/O должен быть постоянным всегда. Secondary никогда не сидит полностью disconnected.

Для стандартного устройства:

Primary   = persistent Exclusive Owner
Secondary = persistent Input Only

takeover requires new Exclusive Owner Forward_Open

Для нашего HA-aware устройства:

Primary   = persistent Owner-A
Secondary = persistent Owner-B standby

takeover does NOT require a new connection

Rockwell показывает, что оба подхода практически реализуемы: обычные output modules firmware-ограничены одним owner, а специальные Redundant Owner modules позволяют двум owner connections существовать одновременно и используют OwnerClaim/OwnerReady для arbitration.

Именно поддержку обоих режимов я бы заложил в I/O contract сейчас. Тогда ни EtherNet/IP timeout/Forward_Open, ни будущий быстрый preconnected takeover уже не потребуют ломать архитектуру.

Давай проверим твои выводы про io адвокатом дьявола

Проверка «адвокатом дьявола» изменила мой вывод в одном важном месте: основа правильная, но я слишком рано назвал per-module ownership достаточным fencing-механизмом. Он гарантирует «два PLC не управляют одним физическим каналом одновременно», но сам по себе ещё не гарантирует согласованный takeover всего I/O-набора.

1. Первое исправление: Redundant Owner — не наша выдумка

Здесь мой предыдущий вывод был слишком осторожным. CIP действительно стандартизует Redundant Owner: несколько controllers могут иметь redundant-owner connections, используя COO — Claim Output Ownership — и ROO — Ready for Ownership. Но ODVA отдельно отмечает, что этот механизм не закрывает всю системную HA-задачу и в EtherNet/IP распространён значительно меньше, чем был в ControlNet; поэтому производители построили собственные системные решения поверх него.

Rockwell реализует буквально:

Owner A connection ──┐
                     ├── Output module
Owner B connection ──┘

OwnerClaim
OwnerReady
OwnerActive
OwnerID

и обе owner connections могут существовать одновременно.

Schneider M580 делает ещё интереснее: оба PAC постоянно поддерживают independent redundant owner connection к каждому RIO drop, поэтому при switchover новый Primary продолжает работать через уже существующее соединение. Schneider прямо связывает это с bumpless RIO switchover.

Значит фундамент:

GENERIC_EIP
HA_REDUNDANT_OWNER

правильный.

Но HA_REDUNDANT_OWNER не надо считать гарантированной возможностью любого EtherNet/IP устройства.

2. Наше утверждение про Input Only оказалось слишком оптимистичным

Текущая спецификация говорит, что non-ACTIVE использует Input Only, а не Listen Only, именно потому что Listen Only зависит от owner.

Логика правильная. Но generic EtherNet/IP output module не обязан предоставлять нам независимый Input Only connection именно в том виде, который нам нужен.

Например стандартные Rockwell output-модули широко используют Listen Only. И документация прямо говорит: если owner connection исчезает, Listen Only тоже прекращает получать данные.

ODVA interoperability tests тоже допускают:

Exclusive Owner
+
Input Only OR Listen Only

в зависимости от возможностей конкретного target.

Поэтому правильный descriptor:

ObserverCapability =
    INDEPENDENT_INPUT_ONLY
    LISTEN_ONLY
    NONE

а не hardcoded:

Secondary = Input Only

Для наших собственных I/O мы, конечно, реализуем независимый observer.

3. Самая серьёзная атака: независимые output-модули могут выбрать разных владельцев

Представим:

DO1     A → B
DO2     A → B
DO3     A → B
DO4     A → B

B начинает takeover.

Из-за разных задержек:

t1:

DO1 owner = B
DO2 owner = B
DO3 owner = A
DO4 owner = A

Каждый отдельный модуль соблюдает:

only one owner

Но система в целом уже:

PLC-A controls part of process
PLC-B controls another part

Это functional split across the I/O set.

Особенно интересно, что стандартный Rockwell Redundant Owner сам по себе этого глобально не решает. Если оба owners имеют OwnerClaim=1, активным становится тот, чей переход 0→1 конкретный модуль получил последним.

Для одного модуля это прекрасно.

Для 50 независимых модулей порядок прихода пакетов может различаться.

Это не обвинение Rockwell — их системная redundancy архитектура имеет дополнительные координационные слои. Но нам нельзя копировать только COO/ROO и считать задачу решённой.

4. И вот здесь CLAIMED_DISARMED неожиданно становится ещё важнее

Наше расширение решает большую часть этой проблемы.

Пусть B получает ownership:

DO1 = B / DISARMED
DO2 = B / DISARMED
DO3 = A / ACTIVE
DO4 = A / ACTIVE

B ещё ничего не выводит.

При захвате DO1 старое A перестаёт воздействовать именно на DO1, а DO1 переходит в configured transition state:

HOLD_LAST
или
SAFE_VALUE

Затем:

DO1 B/DISARMED
DO2 B/DISARMED
DO3 B/DISARMED
DO4 B/DISARMED

Только после этого:

ALL_REQUIRED_OWNED = TRUE

и разрешается:

ARM

Получаем гораздо более сильный invariant:

partial new ownership
        =>
new owner outputs physically DISARMED

А существующая спецификация уже требует, чтобы partial ownership никогда не означал ACTIVE.

То есть CLAIMED_DISARMED я после атаки не выбрасываю, а наоборот повышаю до фундаментального требования наших HA-aware I/O.

5. Но появляется ещё более неприятная атака на Epoch

Раньше мы рассуждали:

A epoch = 41
B takeover → epoch = 42

и I/O принимает 42.

На первый взгляд отлично.

Но при partition:

A: "я хочу epoch 42"

B: "я тоже хочу epoch 42"

или ещё хуже:

A sees 42 → creates 43
B sees 43 → creates 44

Если I/O использует правило:

higher epoch wins

мы создали distributed bidding war.

Поэтому:

Epoch не является fencing authority.

Он нужен для:

reject stale packets
reject stale reconnect
reject old output image
detect replay
identify ownership generation

но не для ответа:

«имеет ли B право выкинуть живого A?»

Текущая спецификация правильно говорит epoch dominates generation, но из этого нельзя выводить largest epoch automatically owns.

6. Нужен ещё один фундаментальный механизм: Owner Lease

Вот чего не хватало в предыдущем проектировании.

У нашего HA-aware I/O должен быть не просто:

connection alive

а:

active-owner authority alive

Я бы назвал это:

OWNER_LEASE

Active PLC постоянно продлевает его вместе с deterministic O→T traffic:

Controller A

HA supervisor
    ↓
LeaseSeq = 18401
    ↓
Output packet
    ↓
I/O

LeaseSeq = 18402
LeaseSeq = 18403
...

I/O измеряет локально:

last_new_lease_seq_age

Если sequence перестал обновляться:

LeaseSeq 18403
LeaseSeq 18403
LeaseSeq 18403

то даже если:

EtherNet/IP connection = ESTABLISHED
PHY = UP
packets = still arriving

модуль понимает:

OWNER_AUTHORITY_EXPIRED

Это закрывает очень неприятный отказ:

PLC application / HA runtime frozen
Ethernet communications task still alive
NIC keeps sending last output image

Обычный CIP connection watchdog такой случай может вообще не увидеть.

7. И Lease нельзя генерировать network task'ом

Это важно.

Если transport layer сама делает:

LeaseSeq++

то при зависшем runtime она продолжит доказывать жизнь мёртвого контроллера.

Lease должен рождаться только из:

HA Supervisor

или из контролируемого execution commit:

scan commit
→ HA authority tick
→ new lease generation

То есть:

Application scan
      │
      ▼
HA safe point
      │
      ▼
OwnerLease generation
      │
      ▼
EtherNet/IP transport

Network layer может только доставить lease.

Не создавать его.

8. Тогда fencing для наших I/O становится намного сильнее

Нормально:

A:
connection valid
lease valid
owner active

B:
connection valid
ready
not active

B считает A отказавшим.

Он не может просто сказать:

Если:

получаем:

Даже если B ошибся в своих PING/PONG.

Вот это великолепный второй независимый fence.

9. Теперь split-brain становится гораздо сложнее получить

Представим ложный peer failure:

B считает A DEAD

но A реально жив

A продолжает:

LeaseSeq++

I/O видит:

A lease VALID

Поэтому:

B takeover request → REJECT

И вся пара:

REDUNDANCY_LOST / takeover failed

а не два владельца.

Это прямо соответствует исходной философии документа:

silence makes a claimant, never an owner; I/O target is the last fence.

Только теперь этот fence становится явным протоколом, а не просто надеждой на CIP connection timeout.

Переход не произойдёт раньше, чем оба независимых доказательства согласны:

11. Generic EtherNet/IP, конечно, этого не умеет

И это принципиально.

У стороннего стандартного output:

OWNER_LEASE

скорее всего отсутствуют.

Там остаётся:

          ↓

Rockwell, например, позволяет на connection fault выбирать Hold Last State либо user-defined fault value — то есть поведение после потери owner является конфигурационной политикой самого output module.

Поэтому IronPLC должен иметь два разных уровня гарантий, а не пытаться притвориться, что они одинаковы.

13. Ещё одна атака: ARM не делает все outputs атомарными

Допустим ownership всех 50 модулей уже B:

...
DO50 B/DISARMED

Посылаем:

Пакеты приходят:

DO1  t=0.1ms
DO2  t=0.3ms
...
DO50 t=1.8ms

То есть физические outputs не включатся одновременно.

Это не split-brain: все уже принадлежат B.

Но это не:

atomic physical output transition

И эти понятия нельзя смешивать.

Наш обязательный инвариант:

ownership atomicity

можно выполнить.

Но:

simultaneous physical actuation

— отдельная feature.

Для неё нужен:

ARM_AT_TIME
+
CIP Sync/PTP

или локальный rack/drop coordinator.

Rockwell уже имеет scheduled output modes с CIP Sync timestamps для некоторых output modules, что подтверждает саму модель scheduled actuation.

Но я бы не включал это в обязательный HA v1.

14. Ещё один сильный вывод даёт Schneider

Это заставляет серьёзно подумать об архитектуре наших I/O:

Это потенциально намного сильнее и проще, чем distributed transaction между 30 независимыми Ethernet targets.
