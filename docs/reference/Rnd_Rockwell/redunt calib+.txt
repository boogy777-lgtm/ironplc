Причём калибровать надо не только Ethernet. Калибруется вся цепочка:

PLC-A HA task
 → driver
 → NIC/PHY
 → cable/SFP
 → NIC/PHY
 → driver
 → PLC-B HA task
 → reply
 → обратно

То есть мы измеряем реальное время, которое важно для HA.

Но ты абсолютно прав: scan нельзя потерять

Более того, здесь есть два разных влияния scan.

Первое — scan влияет на саму достоверность детекта

Если HA processing конкурирует с PLC execution, то при тяжёлом scan может появиться:

PING приехал вовремя
     ↓
HA task не получила CPU
     ↓
PONG задержался
     ↓
ложный failure

Поэтому наша измеренная задержка должна включать режим:

CPU = realistic worst load
PLC application = running
I/O = running
crossload = running

А не calibration на пустом контроллере.

Иначе calibration бессмысленна.

Второе — после решения о takeover ещё надо реально начать управлять выходами

Пусть мы решили:

t0 = Primary failed

Через Tf:

t1 = failure confirmed

Но это не время восстановления процесса.

После этого ещё:

CLAIMING
→ ownership acquisition
→ I/O verification
→ resume
→ safe scan point
→ output image publication

Поэтому реальный параметр, который должен интересовать инженера:

$$ T_{process\_recovery} $$

а не только T_peer_detect.

Формула становится такой
$$ T_{FAILOVER} = T_{DETECT} + T_{DECISION} + T_{CLAIM} + T_{RESUME} + T_{SCAN} + T_{OUTPUT} $$

Где:

T_DETECT
    выбранное после calibration время
    подтверждения отказа

T_DECISION
    время HA FSM

T_CLAIM
    Exclusive Owner / fencing

T_RESUME
    восстановление execution context

T_SCAN
    ожидание/выполнение необходимого scan segment

T_OUTPUT
    фактическая публикация нового output image

И вот T_SCAN нельзя просто считать текущим средним scan.

Нужен минимум:

scan EMA10
scan EMA100
scan max
scan jitter envelope
Очень важный пример

Пусть:

Channel:
    RTT typical = 0.4 ms
    worst calibrated = 0.9 ms

Engineer chooses:
    peer failure confirm = 5 ms

Ownership barrier:
    7 ms

PLC scan:
    average = 8 ms
    worst calibrated = 12 ms

Наивный UI сказал бы:

Failover = 5 ms

что почти ложь.

На самом деле:

Detection           5 ms
HA decision       0.2 ms
Claim               7 ms
Wait/resume scan   ≤12 ms
Output publication  1 ms
-------------------------
Worst recovery     ~25 ms

Именно 25 ms должно видеть инженер.

Можно сделать ещё лучше: scan phase тоже учитывать online

Потому что ждать полный scan приходится не всегда.

Если Primary умер, когда резервный resume point находится практически у output commit:

remaining_scan ≈ 0.5 ms

А если сразу после commit:

remaining_scan ≈ почти Tscan

Поэтому:

$$ T_{SAFEPOINT} = T_{next\_commit}-t_{takeover} $$

и:

$$ 0 \le T_{SAFEPOINT} \le T_{SCAN,max} $$

Тогда online estimator может показывать одновременно:

Predicted if failover happened now:
    14.8 ms

Guaranteed/calibrated worst case:
    25.1 ms

Вот это уже очень мощно.

Я бы поэтому ввёл два разных пользовательских параметра

Не один timeout.

Peer Failure Confirmation
после какого времени отсутствия валидного
peer response считаем peer failed

Например:

5 ms
Maximum Process Recovery Budget

Например:

30 ms

А Studio проверяет:

$$ T_{detect} + T_{claim,max} + T_{scan,max} + T_{output,max} \le T_{recovery-budget} $$

Если:

Configured budget = 20 ms

calculated worst case = 25.1 ms

IDE говорит:

HA requirement cannot be guaranteed.

Minimum demonstrated budget:
25.1 ms

А не молча принимает настройку.

И calibration должна быть периодической

Первичная:

COMMISSIONING_CALIBRATION

даёт baseline.

После этого в RUN постоянно работает:

ONLINE_ADAPTATION

через наши:

EMA10
EMA100
jitter estimator
max observed

Если реальность начинает выходить из calibrated envelope:

baseline RTT     0.3 ms
current EMA10    1.4 ms
scan jitter      ×3

мы не обязаны сразу менять failover threshold.

Но обязательно можем поднять:

HA_PERFORMANCE_DEGRADED

А если гарантированный recovery budget больше не выполняется:

HA_TIMING_GUARANTEE_LOST

Это уже очень ценная промышленная диагностика.
