# Design: Diagnostic Severity

status: implemented
date: 2026-10-16

## Overview

A diagnostic has a category, named `Severity` in the code: one of the seven
message categories of CODESYS. The category belongs to the problem code. Only a
fatal error and an error stop the build; a warning, an information message and a
text are shown and do not. The decision and its alternatives are in
[ADR-0081](../adrs/0081-a-diagnostic-takes-its-category-from-its-problem-code.md).
How the category relates to the other concepts of a message (areas, handling,
suppression, limits, user messages) is defined in
[Message Ontology](message-ontology.md).

Every problem code is an error but one: P4083, the comparison of values of two
different enumerations, is the first warning
([The first warning](#the-first-warning)). This document specifies the
mechanism, so that a code that declares another category behaves as the category
does in every consumer.

## The categories

| Category | Stops the build | Shown | When suppressed | `name()` |
|----------|-----------------|-------|-----------------|----------|
| `FatalError` | yes | yes | stays | `fatal-error` |
| `Error` | yes | yes | stays | `error` |
| `Warning` | no | yes | `SuppressedWarning` | `warning` |
| `Information` | no | yes | `SuppressedInformation` | `information` |
| `Text` | no | yes | stays | `text` |
| `SuppressedWarning` | no | no | stays | `suppressed-warning` |
| `SuppressedInformation` | no | no | stays | `suppressed-information` |

The order is that of CODESYS (`Severity.cs`). A category that cannot be
suppressed stays as it is, as in CODESYS.

## Category of a problem code

`compiler/problems/resources/problem-codes.csv` has the columns
`Code,Name,Message,Severity,Codesys`. The value of `Severity` is `FatalError`,
`Error`, `Warning`, `Information` or `Text`. The two suppressed categories are
never declared: they are only the result of a suppression.

The value of `Codesys` is the CODESYS code that reports the same condition, `C`
and four digits (`C0046`), or empty. A row names a CODESYS code only where the
decompiled checker confirms that it reports the same condition; a code that is
close but not the same stays empty.

**REQ-DS-problems-001** `Problem::severity()` returns the `Severity` of the
problem's row.

**REQ-DS-problems-002** `Severity::name()` returns the text of the table above
for each of the seven categories.

**REQ-DS-problems-003** `Severity::stops_build()`, `Severity::is_shown()` and
`Severity::suppressed()` answer as the table above for each of the seven
categories, and a suppressed category suppressed again is itself.

**REQ-DS-problems-004** A row of `problem-codes.csv` whose `Severity` is missing,
unknown or a suppressed category fails the build, and the error names the code
and the value.

**REQ-DS-problems-005** The header of `problem-codes.csv` is
`Code,Name,Message,Severity,Codesys`; any other header fails the build.

**REQ-DS-problems-006** `Problem::codesys()` returns the `Codesys` value of the
problem's row, and `None` for a row whose value is empty.

**REQ-DS-problems-007** A row of `problem-codes.csv` whose `Codesys` is neither
empty nor `C` and four digits fails the build, and the error names the code and
the value.

**REQ-DS-problems-008** `Severity::script_name()` returns the name of the category
in the CODESYS scripting model and `Severity::script_value()` its value in the
CODESYS `Severity` flag set, for each of the seven categories: 1, 2, 4, 8, 16,
32 and 64 in the order of the table above.

**REQ-DS-problems-009** `Severity::person_word()` returns `Error` for a fatal
error and an error, `Warning` for a warning and `Information` for an information
message, and `None` for a text and for the two suppressed categories.

The enumeration `Severity`, its questions and the matches of
`Problem::severity()` and `Problem::codesys()` are generated by
`problems/build.rs` from the one list of categories in `problems_gen`. The
matches name every category and every problem and have no wildcard arm.

## Category of a diagnostic

**REQ-DS-dsl-001** A `Diagnostic` has the category of its problem, whichever
constructor made it. No call site sets the category.

**REQ-DS-dsl-002** `Diagnostic::stops_build()` is true for a diagnostic of
category `FatalError` or `Error` and false for one of any other category.

**REQ-DS-dsl-003** `any_stops_build` is true when at least one diagnostic of a
list stops the build, and `stops_build_count` counts them; a list without a
fatal error or an error does not stop the build.

**REQ-DS-dsl-004** `Diagnostic::suppress()` turns a warning into a suppressed
warning and an information message into a suppressed information message, and
leaves a diagnostic of any other category as it is. It is the one way to change
the category of a diagnostic after it is made.

**REQ-DS-dsl-005** `stop_at_fatal` returns only the fatal errors of a list that
holds one, and the list as it is otherwise.

## Forms of a diagnostic

A diagnostic has two forms, both generated from the one list of categories: the
header a person reads and the fields a program reads
([Message Ontology](message-ontology.md#message-forms)).

**REQ-DS-dsl-006** `Diagnostic::codesys()` returns the `Problem::codesys()` of the
problem of the diagnostic, whichever constructor made it.

**REQ-DS-dsl-007** `Diagnostic::person_header()` is the word of the category, the
code in brackets, and `(CODESYS Cnnnn)` when the problem has a CODESYS code, as
in `Error[P4007] (CODESYS C0046)`. It is `None` for a text and for a suppressed
category.

**REQ-DS-dsl-008** `Diagnostic::person_text()` is the text of the primary label
when it has one and the description otherwise: the line a person reads for a
text, with no header and no code.

**REQ-DS-dsl-009** `Diagnostic::script_message()` has the fields of the CODESYS
`ScriptMessage` that a diagnostic has: `severity`, `severity_value`, `prefix`,
`number`, `text`, `position` (the byte offset), `length`, `position_text`
(`file:line:column` counted from 1, when the text of the file is known) and
`object` (the file).

**REQ-DS-dsl-010** `ScriptMessage` has, for each of the seven categories, the
scripting name as `severity` and the value of the CODESYS flag set as
`severity_value`, and `is_in` tells whether that value is in a mask of
categories.

**REQ-DS-dsl-011** `ScriptMessage` has the CODESYS code of the problem as
`codesys`, and null where the problem has none.

## Messages without a code

A problem code gives a diagnostic its category and its text. Some messages have
no problem: the line CODESYS keeps when a limit is passed, and the lines that
open and close a build. CODESYS stores them as messages of its own with the id
`None` (`CompilerMessage.cs:285-295`); the message ontology numbers this MSG-040.

Their texts are rows of a second table of the message dictionary
([ADR-0082](../adrs/0082-a-message-without-a-problem-code-is-a-row-of-its-own-table.md)),
`compiler/problems/resources/codeless-texts.csv`, with the columns
`Key,Severity,Template`. The row declares the category because there is no
problem to take it from, and the key replaces the code as the identity of the
message. The template has the placeholders of `problem-texts.csv`. The build of
the problems crate makes `ironplc_problems::codeless::<key>(...)`, which returns
a `CodelessText`, one function for each row; there is no other way to make one,
so no text and no category of a message without a code is written at a call
site.

**REQ-DS-problems-010** The header of `codeless-texts.csv` is
`Key,Severity,Template`. A row whose `Severity` is missing, unknown or a
suppressed category, whose key is not snake_case or is used by an earlier row, or
whose template has a malformed placeholder fails the build, and the error names
the line and the key.

**REQ-DS-problems-011** A function of `codeless` returns a `CodelessText` that has
the key and the category of its row and the template with the arguments in place;
the texts of the limit lines, the build lines and the compile lines are those of
CODESYS (`en.json`: `ErrorLimitExceeded`, `WarningLimitExceeded`, `BuildStarted`,
`BuildCompleteOK`, `BuildCompleteErrors`, `CompileCompleteOK` and
`CompileCompleteErrors`), including the spelling "occured".

**REQ-DS-dsl-012** `Diagnostic::codeless` makes a diagnostic from a `CodelessText`
that has no code (`has_code()` is false and `code` is empty), the category and
the key of its row, no CODESYS counterpart and no place: it points into no file.

**REQ-DS-dsl-013** The person form of a message without a code is the word of its
category alone, `Error` or `Warning`, with no brackets and no code, and `None` for
a text; `person_text()` is its text.

**REQ-DS-dsl-014** The program form of a message without a code has the text of
the row, the scripting name and value of its category, `prefix`, `number` and
`codesys` null, an empty `object` and no `position_text`.

## What a run keeps

A run collects the messages of its stages in the order they are produced. What
the run keeps of them is decided in one place, the keep rule of the area the run
writes (`Area::keep`, [Message areas](#message-areas)), which the places that
collect the messages of a run apply
([What a build and a check keep](#what-a-build-and-a-check-keep)); a consumer
that shows the messages never decides it. This section describes the rule of the
Build area, `ironplc_dsl::diagnostic::kept`. The rules are those of CODESYS
(`Messages.cs:28-43`, `-.351.cs:65-75`, `-.352.cs:93-215`), with one difference
by the owner's decision: the warning limit is 500, not 100.

- A fatal error ends the run, as above.
- The messages keep the order in which they were produced; nothing is sorted.
- A message that repeats an earlier one is dropped and the first stays: the same
  code, category, place and text.
- At most 500 errors (`FatalError` and `Error`) and at most 500 warnings
  (`Warning`) stay. At the first message over a limit, one line of the kind stays
  in its place, "More than 500 errors occured: Skipping all further error
  messages" as an `Error` or "More than 500 warnings occured: Skipping all further
  warning messages" as a `Warning`, and the messages of that kind after it are
  dropped.
- Once the error limit is passed, the related positions (the secondary labels) of
  the messages that follow are dropped.

Each limit is declared with the line of its kind in one entry of one table, so a
new kind of limit is one entry. A limit line is not counted against its limit, and
`kept` applied to its own result changes nothing, so each layer of a pipeline can
apply it.

**REQ-DS-dsl-015** `kept` keeps the messages in the order they were produced and
does not sort them.

**REQ-DS-dsl-016** `kept` drops a message that has the same code, category, place
and text as an earlier one, and the earlier one stays; the same text at another
place, or in another category, is not a repeat.

**REQ-DS-dsl-017** `kept` keeps 500 errors as they are, and for 501 or more keeps
the first 500, then one line "More than 500 errors occured: Skipping all further
error messages" of category `Error` without a code, and no later error.

**REQ-DS-dsl-018** `kept` keeps 500 warnings as they are, and for 501 or more
keeps the first 500, then one line "More than 500 warnings occured: Skipping all
further warning messages" of category `Warning` without a code, and no later
warning; the two limits are independent, so a run over both limits has both lines
and its messages of other categories.

**REQ-DS-dsl-019** `kept` drops the related positions of the messages that follow
the error limit, and keeps those of the messages before it, the 500th error
included.

**REQ-DS-dsl-020** `kept` applied to its own result returns it unchanged, and a
message added after a limit line is still over the limit without a second line.

## Summary lines

A build and a check end with a line that gives the counts of the run, which
CODESYS stores as a message of category `Text` without a code
(`CompilerPhaseControllerGenerateCode.cs:656-686`,
`CompilerServicesInternal.cs:1246-1274`,
`LanguageModelManagerConsolidated.cs:1972-1989`, `-.404.cs:275`). So they are
messages like any other: both forms show them, the person form as the plain line,
the program form as a `Text` with a null `prefix` and `number`, and the language
server sends them to the Output channel.

- `check` ends with "Compile complete -- {errors} errors, {warnings} warnings".
- `compile` starts with "------ Build started: Application: {application} -------"
  and ends with "Build complete -- {errors} errors, {warnings} warnings : Ready
  for download", or "… : No download possible" when an error stops the build.
- The application is the `CONFIGURATION` that is built: its name, as written. A
  program with several configurations is named for the first one written, which
  is the one code generation compiles. A program with no `CONFIGURATION`, and a
  program whose analysis produced no library (a syntax error), has none to name,
  and the name is that of the project: the file name without its extension of a
  file given to the command, or the name of the directory. This is the owner's
  decision; CODESYS names the application of its project, and IronPLC has no
  application object. One function reads it, `Project::application_name`, and the
  command line and the MCP tool `compile` both ask it.
- The counts are those of the messages the run kept, which is the state of the
  pipeline as it ends: `FatalError` and `Error` are errors, only `Warning` is a
  warning, and a build can succeed with warnings. The counts include the limit
  lines (MSG-075, the owner's decision: CODESYS counts what it stores, and it
  stores the limit line as an `Error` or a `Warning`), so a run that passes the
  error limit reports 501 errors.

Each command declares its lines in one constant (`CHECK_SUMMARY`,
`COMPILE_SUMMARY`), and the numbers come from the one function `counts`. The
command line and the MCP tools `check` and `compile` close their run with that
constant, so the framing is one rule and not one copy for each front end.

**REQ-DS-dsl-021** `counts` counts a `FatalError` and an `Error` as errors and a
`Warning` as a warning, and no other category; the limit lines are counted, so a
run that passes the error limit reports 501 errors.

**REQ-DS-dsl-022** `CHECK_SUMMARY.close` returns the messages the run keeps and
then one `Text` "Compile complete -- {errors} errors, {warnings} warnings" with the
counts of the run, for any counts including zero.

**REQ-DS-dsl-023** `COMPILE_SUMMARY.close` returns a `Text` "Build started" with the
name of the application, the messages the run keeps, and then one `Text` "Build
complete" with the counts, ending "Ready for download" when the run has no error
and "No download possible" when it has one.

**REQ-DS-project-005** `Project::application_name` is the name of the
configuration that code generation compiles, as written, and is the fallback it is
given when the analyzed library has no configuration or the analysis produced no
library.

**REQ-DS-analyzer-006** The analyzed library holds the configurations of the
program in the order they were written, so that the first is the one written
first.

## What stops a build

A place that decides that a program is rejected asks `stops_build`, not whether
there are diagnostics.

**REQ-DS-project-001** `ironplc_project::compile` runs code generation and
returns a container when no diagnostic stops the build, and returns no container
when one does, seeded by the caller or found by the analysis.

**REQ-DS-project-002** A fatal error ends the run: when the diagnostics the
caller seeded hold one, `compile` runs no analysis and no code generation, and
when the analysis finds one, it runs no code generation; the diagnostics it
returns are the fatal ones alone.

The other gates are the exit status of every command of the command line
(`finish`), the check that `sync-uids` runs before it writes the sidecar, the
language server's run command, the `ok` of the MCP tools `check`, `parse`,
`pou_lineage`, `pou_scope`, `project_io`, `project_manifest`, `symbols` and
`types_all`, and the fixture guard of the benchmarks. A diagnostic that does not
stop the build is still printed by the command line and published by the
language server.

An analysis pass that collects diagnostics and returns `Err` to stop that pass
(`semantic_rules`, the `xform_*` passes) is not a gate. Its diagnostics are added
to the semantic context, and they reach the gates above.

## What a build and a check keep

The run names its area, and the rule of the area is applied where the messages
of the run are collected ([Message areas](#message-areas)), so the command line,
the language server and the MCP tools never decide it themselves and no caller
can skip it:

- `Project::semantic(area)` returns the messages that parsing and analysis
  produced, kept by `area.keep`. The area is a parameter of the run, so a caller
  that does not name one does not compile;
- `ironplc_project::compile` writes the Build area. It returns the messages of
  its seeded diagnostics, the analysis and code generation together, kept by
  `Area::Build.keep`, so the limit is over the whole run; the analysis inside it
  is `semantic(Area::Build)`, and keeping again is idempotent;
- the command `check` and `compile` close their run with a `Summary`, which
  declares its area and applies the rule of it to what the command collected
  (the idempotence of `kept` keeps the limit lines single);
- the MCP tools run `semantic(Area::Build)`, or the area they are asked for
  (`get_message_objects`, `get_messages`);
- the language server runs `semantic(Area::Precompile)`.

**REQ-DS-project-003** `compile` returns the messages its run keeps: for 501 errors
the first 500 and the line of the limit, for 500 errors all of them and no line,
for 501 warnings the first 500, the line of the limit and the container, and the
limit is over the seeded diagnostics and the analysis together.

**REQ-DS-project-004** `Project::semantic` keeps the messages by the rule of the
area it is given: for 501 errors, `Build` returns the first 500 and the line of
the limit (and the same for 501 warnings), and `Precompile` returns all 501 and no
line.

## Message areas

CODESYS keeps its messages in separate lists, and a viewer shows one list at a
time ([Message Ontology](message-ontology.md#message-area)). In IronPLC a list is
an `Area` (`ironplc_dsl::diagnostic::Area`), a class whose members declare
themselves:

| Area | CODESYS list | Written by |
|---|---|---|
| `Build` | `CompilerMessageCategory` | `ironplcc check`, `ironplcc compile`, the MCP tools, the playground's compile |
| `Precompile` | `PreCompileMessageCategory` | the language server's analysis while editing |

An area declares its `name` (the name of the Messages view), its `source` (the
text an editor shows as the source of a diagnostic), a `description`, its
`capacity` and its keep rule, each in a `match` with an arm for each member and
no wildcard. A new area is one new member: the compiler then asks for each of
these, and no consumer of the class changes. The Output channel of the editor is
a place (`Place` in the language server), not an area.

A run writes exactly one area. A message declares the areas it is shown in
(`ShownIn`, the CODESYS `ShowAttribute`) when it is made: a message made with a
position is shown in every area, and a message made without one
(`Diagnostic::codeless`) is shown in `Build` alone, because CODESYS clears
`Precompile` from the `ShowAttribute` of a message made without a position
(`CompilerMessage.cs:26-60`). It is a field set at the construction, not a test
of the place made by the consumer. A message without a code that has a position,
such as the message of a pragma in the source, is made by its own constructor,
and that sets every area.

**REQ-DS-dsl-024** `Area::ALL` holds each member once, at its `index`, and each
area declares a name, a source and a description: `Build` is named "Build" with
source "IronPLC Build", and `Precompile` is named "Precompile" with source
"IronPLC Precompile".

**REQ-DS-dsl-025** A message made with a position is shown in every area; a
message made by `Diagnostic::codeless`, such as a limit line or a summary line, is
shown in `Build` alone.

### What each area keeps

**REQ-DS-dsl-026** `Area::Build.keep` keeps what `kept` keeps, as
[What a run keeps](#what-a-run-keeps) describes: no repeats, at most 500 errors
and 500 warnings with the line of each limit.

**REQ-DS-dsl-027** `Area::Precompile.keep` keeps, in the order produced, the
messages that are shown in `Precompile` and are not suppressed, and drops a
repeat of an earlier message. It writes no line of a limit and a fatal error does
not end the run, because the precompile of CODESYS has neither
(`PreCompileContext.cs:2440-2525`; the owner confirmed it); applied to its own
result it changes nothing.

The Precompile area holds at most 950 messages. CODESYS applies the limit twice
(`PreCompileContext.cs:2440-2525`):

- the precompile of one object collects the messages that are shown in
  `Precompile` and stops at 950 (`list.Count == 950`, `break`);
- it then removes the earlier messages of that object from the area, and when
  the area would hold more than 950 in total, it removes the oldest messages of
  the area, the first stored, so that the total is at most 950
  (`AddNewMessagesToMessageStorage`).

So the limit is 950 messages per object in one precompile **and** 950 messages in
the whole area, with the oldest dropped, and not 950 per object only.

IronPLC has no object granularity in the language server: it analyses the whole
workspace on each edit and publishes per file (LSP `publishDiagnostics` is per
document). The IronPLC decision is that **the object is the file**:

- each file holds at most its first 950 messages;
- the area holds at most 950 in total; the files are written in ascending order
  of their URI and the file that was edited last, which plays the role of the
  object just precompiled, is written after them, so the messages of the files
  written first are removed first;
- a message published to several files (its secondary labels are in other files)
  counts once for each file it is published to.

`Area::store` is that rule, for any kind of object; the area without a capacity
(`Build`) stores everything it is given.

**REQ-DS-dsl-028** `Area::Precompile.store` keeps the first 950 messages of an
object, and when the total of the objects it is given, oldest first, is over 950
removes the oldest messages first until the total is 950; `Area::Build.store`
returns what it is given.

## The first warning

P4083 (`EnumerationTypesCompared`) is a `Warning` with the CODESYS counterpart
C0354 `Wrn_EnumComparison`, "Comparison of one enumeration type ({0}) with
another ({1})", raised where CODESYS compares the types of the two operands of a
comparison (`Phase4_TypeCheck/TypeCheckerVisitor.cs:5423-5438`): both operands are
enumeration types and they are different enumeration types. CODESYS asks no more
than that, so the warning does not depend on whether either enumeration is
strict (the `strict` attribute, [Attributes](attributes.md#strict-and-not-strict)),
and a comparison of two different enumerations is accepted either way.

The places that compare are the relational operators `=`, `<>`, `<`, `<=`, `>` and
`>=`, their function forms `EQ`, `NE`, `LT`, `LE`, `GT` and `GE`, and the
selection functions `MIN` and `MAX`; `LIMIT`, `SEL` and `MUX` do not compare their
inputs with each other. Each place declares that it compares (the use
`ValueUse::Compares`: the operator by `ValueUse::of_compare`, a function by its
row), and the check asks that declaration, never a name.

Two operands are of the same enumeration when `enumeration_declaration` of their
types is the same: a type alias (`TYPE E3 : E1;`) is the enumeration it names, as
it is for the values of an enumeration and for `strict`. A reference to an
enumeration, an integer, an untyped literal and a value of the enumeration itself
are not enumerations of two types, as in CODESYS, which asks the class of the
operand type and does not dereference it.

**REQ-DS-analyzer-001** A comparison operator, the function form of one, `MIN` and
`MAX` whose two operands are values of two different enumerations report P4083,
once, whether either enumeration is strict or neither is.

**REQ-DS-analyzer-002** P4083 is a warning with the CODESYS counterpart C0354. Its
primary label is the whole comparison or call, and its text names the declared
types of the left and of the right operand: "Comparison of one enumeration type
(E1) with another (E2)". It does not stop the build.

**REQ-DS-analyzer-003** An alias of an enumeration is the enumeration it names: its
comparison with that enumeration is not reported, and its comparison with another
enumeration is, naming the alias.

**REQ-DS-analyzer-004** A comparison with an integer or an untyped literal, with a
value of the same enumeration, with a reference to an enumeration, and a call of
`LIMIT`, `SEL` or `MUX` are not reported.

**REQ-DS-analyzer-005** P4083 is raised for a comparison independently of the
other problems of the program, as CODESYS raises it: a program with an error of
another cause has the error and the warning, and a comparison of two
enumerations has the warning and no error for the comparison.

## What each consumer shows

Each consumer that has a type of its own for a category maps `Severity` with a
`match` that has no wildcard arm, and takes every word, name and value of a
category from the list of categories (`Severity::person_word()`,
`script_name()`, `script_value()`, `name()`), never from a literal of its own.
A message has two forms ([Message Ontology](message-ontology.md#message-forms)):

- **For a person** (the command line and the editor) with the words of the
  CODESYS Messages view.
- **For a program** (MCP and the JSON output of the command line) with the
  fields of the CODESYS scripting class `ScriptMessage` and the scripting names
  of the categories.

| Category | Command line header | Language server | `severity` (`severity_value`) in MCP and JSON | Playground `severity` |
|----------|---------------------|-----------------|-----------------------------------------------|-----------------------|
| `FatalError` | `Error` | `ERROR` | `FatalError` (1) | `fatal-error` |
| `Error` | `Error` | `ERROR` | `Error` (2) | `error` |
| `Warning` | `Warning` | `WARNING` | `Warning` (4) | `warning` |
| `Information` | `Information` | `INFORMATION` | `Information` (8) | `information` |
| `Text` | the text alone, no header, no code | not a diagnostic; `window/logMessage` of type `INFO` | `Text` (16) | `text` |
| `SuppressedWarning` | not shown | not published | `SuppressedWarning` (32) | not shown |
| `SuppressedInformation` | not shown | not published | `SuppressedInformation` (64) | not shown |

### The command line

The header of a message is its word, its code in brackets and, when the problem
has a CODESYS counterpart, that code: `Error[P4007] (CODESYS C0046): <text>`.
codespan draws the source snippet below the header and its own header is not
written.

**REQ-DS-cli-001** The command line writes the header
`Diagnostic::person_header()` gives for a fatal error, an error, a warning and an
information message, followed by `: ` and the description, and the source
snippet below it.

**REQ-DS-cli-002** The command line writes a text as its plain line, with no
header and no code, and writes a suppressed warning and a suppressed information
message not at all.

**REQ-DS-cli-003** `ironplcc check --format json` writes to the standard output
one JSON array that holds the `ScriptMessage` of every message the run keeps, a
suppressed one included, and then the message "Compile complete" that closes the
check; a program without a problem has that message alone.

**REQ-DS-cli-005** `ironplcc check` writes a warning with its header
(`Warning[P4083] (CODESYS C0354)`) and its source snippet, and exits with status
0; `ironplcc compile` of the same program writes the container and exits with
status 0.

**REQ-DS-cli-006** `ironplcc check` ends with the line "Compile complete -- {errors}
errors, {warnings} warnings", a text without a header, with the counts of the
messages the run kept: 0 and 0 for a program without a problem, 1 and 0 for one
error, 0 and 1 for one warning. It does not change the exit status.

**REQ-DS-cli-007** `ironplcc compile` of a program that has only a warning starts
with the line "------ Build started: Application: {name} -------", where the name
is the file name without its extension (or the name of the directory) when the
program has no `CONFIGURATION`, writes the warning, ends with "Build complete -- 0
errors, 1 warnings : Ready for download", writes the container and exits with
status 0.

**REQ-DS-cli-014** `ironplcc compile` and `ironplcc check --format json` of a
program that has a `CONFIGURATION` name the application for it: the line "Build
started" gives the name of the configuration, and the first one written when there
are several, whatever the name of the file.

**REQ-DS-cli-008** `ironplcc compile` of a program that has an error ends with
"Build complete -- 1 errors, 0 warnings : No download possible", writes no
container and exits with a failure status.

**REQ-DS-cli-009** `ironplcc check --format json` gives the closing line as a
message of category `Text` (16) with a null `prefix` and `number`, last in the
array.

**REQ-DS-cli-010** A message without a code that is an error or a warning is
written on one line, its word and its text, as `Error: More than 500 errors
occured: Skipping all further error messages`, with no source snippet and no link,
and `ironplcc check` of a source with 501 errors writes 500 errors, that line and
"Compile complete -- 501 errors, 0 warnings", and fails.

### The language server

A fatal error and an error are errors of the Problems panel, a warning is a
warning and an information message is an information, the three switches of the
panel, as in the CODESYS Messages view. A text is a line about the build and not
a problem of a file: it is sent as a `window/logMessage` of type `INFO` (type
`LOG` is written at the debug level, which the output channel of the language
client hides by default), so that it appears in the Output channel.

**REQ-DS-cli-004** The language server publishes a fatal error and an error with
severity `ERROR`, a warning with `WARNING` and an information message with
`INFORMATION`, sends the text of a `Text` as a `window/logMessage` of type `INFO`
and does not publish it as a diagnostic, and publishes a suppressed warning and a
suppressed information message not at all.

**REQ-DS-cli-011** The language server publishes and logs no message that has no
position, such as the limit line of the errors or a closing line, because such a
message is not shown in the Precompile area it writes.

The language server writes the Precompile area ([Message areas](#message-areas)).
The `source` of each diagnostic it publishes is the `source` of the area, which
names the product and the area, so that the Problems filter of the editor can
select the messages of one area. The area also decides what the editor holds.

**REQ-DS-cli-012** The language server publishes every diagnostic with the `source`
of the Precompile area, "IronPLC Precompile", and a message that is about no file
of the workspace but has a position, such as one in the built-in library, is
published for the file edited last.

**REQ-DS-cli-013** The language server publishes at most the first 950 messages of
a file, and at most 950 in all: the files are written in ascending order of their
URI and the file edited last after them, and the messages of the files written
first are removed first. A file that loses all its messages is not published.

### MCP

The tools return a message as a `ScriptMessage` (`serialize_diagnostic`), under
the names of its fields: `severity`, `severity_value`, `prefix`, `number`, `text`,
`position`, `length`, `position_text` and `object`, and `codesys` for the CODESYS
code of the same condition, which CODESYS does not have. The code `P4007` is
`prefix` `P` and `number` 4007. `position` is a byte offset and `length` a number
of bytes, with no line and column conversion, and `position_text` is
`file:line:column` counted from 1, when the text of the file is known.

**REQ-DS-mcp-001** `serialize_diagnostic` writes `Severity::script_name()` of the
diagnostic as its `severity` and `Severity::script_value()` as its
`severity_value`.

**REQ-DS-mcp-002** The `ok` of `check` is false when a diagnostic stops the build
and true when none does. A diagnostic of another category is listed and does not
make `ok` false, because `ok` asks `any_stops_build`.

**REQ-DS-mcp-003** A suppressed diagnostic is serialized, with `SuppressedWarning`
or `SuppressedInformation` as its `severity`, so that a tool can see what was
hidden.

**REQ-DS-mcp-004** `serialize_diagnostic` writes the fields of `ScriptMessage`
and `codesys` (null when the problem has no CODESYS code), and no other name for
the code, the message and the position.

**REQ-DS-mcp-005** The tool `get_message_objects` takes the sources and the options
of `check`, an optional `severities`, a mask of `severity_value`s whose default
is every category (0xFFFFFFFF), and an optional `area` (REQ-DS-mcp-008),
and returns the `ScriptMessage` of each message of the check whose category is in
the mask, as `system.get_message_objects` does: in the Build area, the
messages of `check`, which end with the line "Compile complete" (a `Text`), once.

**REQ-DS-mcp-006** The tool `get_messages` takes the sources and the options of
`check` and an optional `area`, and returns the text of every message and nothing
else, as `system.get_messages` does, from the same messages as
`get_message_objects` with every category.

**REQ-DS-mcp-007** The `ScriptMessage` of a message without a code, such as the
closing line of a check or a limit line, has a null `prefix`, `number` and
`codesys`.

The `diagnostics` of `check` and `compile` are the messages of the run as the
command line frames them, by the one rule `Summary::close`
([Summary lines](#summary-lines)): the closing line is among them, as CODESYS
stores it among its messages, so a program without a problem has that line alone
and `ok`, not the length of the list, says whether a problem stops the build. The
two queries of the messages read the same messages, and return the closing line
once.

**REQ-DS-mcp-010** The `diagnostics` of `check` are the messages the run keeps
and then the line "Compile complete -- {errors} errors, {warnings} warnings" with
the counts of the run, as the command line writes them, whatever ended the run:
an analysis, an invalid `sources` or an invalid `options`. The line is a `Text`,
so it does not change `ok`.

**REQ-DS-mcp-011** The `diagnostics` of `compile` start with the line "------
Build started: Application: {name} -------", where the name is that of the
`CONFIGURATION` that is built and, for a program without one, the name of the
first source without its extension, then hold the messages the run keeps, and end
with "Build complete -- {errors} errors, {warnings} warnings", followed by " :
Ready for download" or, when an error stops the build, by " : No download
possible"; an error found after the analysis, such as a container that does not
fit the cache, is counted in that line. `ok` keeps its meaning.

The scripting queries of CODESYS take the list to read as their `category`
argument. The two queries take it as `area`, by the name the area declares
(`Area::name`), and the tool `get_message_areas` lists the areas
([Message areas](#message-areas)).

**REQ-DS-mcp-008** The tools `get_message_objects` and `get_messages` take an
optional `area`, `Build` by default: the run is made in that area, so that for
`Precompile` the messages are those the language server keeps over the same
sources (the messages that have a position, without a limit line) and there is no
closing line, because the precompile of CODESYS has none; an `area` that no
member declares is not accepted.

**REQ-DS-mcp-009** The tool `get_message_areas` returns, for each area of
`Area::ALL`, its `name`, its `source` and a one-line `description`.

**REQ-DS-playground-001** The playground writes `Severity::name()` of the
diagnostic as its `severity`.

**REQ-DS-playground-002** The playground lists the diagnostics that are shown and
leaves out a suppressed warning and a suppressed information message.
