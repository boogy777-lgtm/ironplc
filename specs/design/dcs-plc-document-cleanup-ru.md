# Очистка документации после принятия DCS PLC Platform v3.0

Дата: 2026-09-23. Репозиторий: `boogy777-lgtm/ironplc`.
База проверки: `lint-fences`, commit `8a7f6d0d09b00436daebfd669babd39f2e0f2e13`.

Финальная спецификация: [DCS PLC Production Platform v3.0](dcs-plc-production-platform-spec-ru.md).
Этот документ — конкретный перечень последующих изменений. При публикации спецификации старые файлы **не удалены и не перемещены**. Принятие целевой архитектуры не означает реализации её требований или прохождения production gates.

## 1. Что удалить из актуального дерева

| Файл | Причина | Замена и условие удаления |
|---|---|---|
| `docs/reference/dcs-firmware-task-v2-ru.md` | Версия 2.0: прежние контексты, FreeRTOS как базовый пример и более узкие границы firmware; создаёт второй источник требований рядом с v3.0. Уже обозначена как историческое owner-provided задание. | v3.0 целиком, особенно §§1–6, 10–11, 17, 25. Перед удалением заменить действующие ссылки, а исторические закрепить на исходном commit. |
| `docs/reference/dcs-firmware-task-v2.2-ru.md` | Версия 2.2: прежняя нормативная база; новые правила binding-first, deployment, authority, RecoveryAdmission и OS-портов должны читаться из одного документа. | v3.0 §§4–11, 17–18, 21, 25. Перед удалением перенести уникальные требования, если сверка обнаружит непокрытые, и обновить ссылки. |

Удаляется файл из текущего дерева, а не история Git. Исторические ссылки должны вести на commit выше, а не на удалённый путь в HEAD. Идентификаторы старых T01/D01 нельзя механически сопоставлять одноимённым T01/DA01 новой версии: нужна проверка содержания.

## 4. ADR: сохранить историю решений

ADR не удалять и не перенумеровывать. Для несовместимых решений оформить новые ADR с отношением supersedes / partially supersedes и явным перечнем сохранённых положений. Номер нового ADR выбрать по актуальному дереву при реализации этой чистки.

| ADR | Что пересмотреть / сохранить |
|---|---|
| 0052 | Сохранить RuntimeHost как владельца локального commit; orchestration deployment вынести в DeploymentCoordinator. |
| 0054–0056 | Проверить границы state migration, hot-edit command layer и process-local host; не распространять ограничения конкретного MCP backend на всю платформу. |
| 0060–0061 | Сохранить явные правила конверсии и инженерные решения; согласовать semanticType, bounded migration и запреты небезопасного override. |
| 0062 | Сохранить измеряемый failover timing; согласовать issuer authority, fencing и условия promotion. |
| 0063 | Сохранить транспортные решения там, где применимы; пересмотреть отложенную security и контракт production API. |
| 0064 | Пересмотреть redundant online change: независимые term/sequence/revision, crash points, RecoveryAdmission до первого эффекта нового поколения, ACK не равен NVM durability. |
| 0065 | Сохранить IDE-side pending edits; согласовать identity и scoped write admission с несколькими authenticated клиентами. |
| 0066 | Сохранить выбор Linux как первичного профиля; заменить глобальный epoch, смешивающий scan и authority, отдельными счётчиками и владельцами. |

ADR-0053 со стабильными идентификаторами переменных сохраняется. ADR-0010/no_std проверяется как отдельная цель и статус реализации, а не удаляется из-за наличия std-зависимостей сегодня. Остальные ADR, язык IEC, compiler/VM design и пользовательские инструкции не подлежат массовому удалению.

## 5. Порядок выполнения чистки и критерии завершения

1. Опубликовать v3.0 и этот перечень в отдельной ветке. Это текущий этап.
2. Зафиксировать новые/частично заменяющие ADR и таблицу old requirement → new requirement / historical / intentionally dropped с причиной. До завершения этого шага наличие спецификации не означает, что все старые ADR уже формально заменены.
3. Обновить design-документы, roadmap и индексы. На оставленных исторических документах явно указать статус.
4. Исправить действующие ссылки на две старые версии ТЗ; исторические ссылки закрепить на commit. Перенести пять аудитов с корректировкой относительных ссылок.
5. Удалить только две версии ТЗ, перечисленные в §1. Не удалять runtime, тесты или целые ветки репозитория в рамках документационной чистки.
6. Проверить ссылки во всём checkout, включая RST, Rust, YAML и скрипты. Проверить, не извлекают ли тесты таблицы/идентификаторы из изменённых документов.
7. Выполнить обязательные gates из `AGENTS.md`: `cd compiler && just` (либо указанный там fallback) и `cd specs && just`, прежде чем открывать PR. Проверить, что diff не содержит несвязанных изменений и что реализованные возможности отделены от целевых требований.
